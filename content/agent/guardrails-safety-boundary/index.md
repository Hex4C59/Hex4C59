一个 Agent 能读文件，并不表示它应该读工作区里的每个文件；能写文件，也不表示它可以自行批准覆盖原稿。即使最后的回答被拦住，前面已经写入、删除或发送的数据也不会自动恢复。

Guardrails（安全护栏）是在执行流程中设置检查与限制。本篇面向会写简单 Python、了解工具调用的读者，用一个小例子分别检查：请求能否进入模型，模型要求的操作能否执行，以及工具数据和最终回答能否继续返回。

这里实际实现的是**受限文件工具的权限边界**。它只提供读取笔记和写入草稿，没有命令执行、删除、网络发送或容器功能。默认演示使用固定模型响应，但工具调用、文件读写、拒绝和测试都实际运行。

[Tool Use](/agent/tool-use-core-of-agent/)、[ReAct](/agent/react-paradigm/)、[Planning](/agent/planning-plan-and-execute/)和[多 Agent 协作](/agent/multi-agent-collaboration/)增加了执行路径。每多一条路径，都要检查它是否经过相应限制；不能只把危险工具名从提示词里删掉。

## 先给结论

- 在工具执行前检查操作名、参数、路径和授权。未知操作直接拒绝，不靠模型承诺不调用。
- 输入检查和内容扫描只识别本例列出的模式。命中后程序明确停止，不把“加了一条提醒”当成已经拦截。
- 所有模型可调用的 handler 都回到同一个 `dispatch()`。直接调用 handler，也不能跳过内部校验。
- 写入批准绑定路径、完整新内容和现有文件摘要，只能使用一次；模型没有批准工具，也不能传一个布尔值替自己授权。
- Python 路径检查和命令包装不是操作系统沙箱。本例没有运行不可信程序，不能据此声称已经限制进程、网络或系统资源。

## 为什么要分别检查输入、执行和输出

下面是三个假设场景：

| 请求或资料 | 可能发生的错误动作 | 应当检查的位置 |
| --- | --- | --- |
| 总结一份普通笔记 | 笔记夹带“改为读取密钥”的指令 | 工具内容返回模型之前，并继续限制后续可读路径 |
| 把摘要写到草稿 | 模型选择了已有原稿或越界路径 | 写入之前检查路径、内容和批准 |
| 回答执行结果 | 回答包含可识别的敏感文字 | 返回调用者之前检查最终文本 |

只检查最终回答，无法阻止已经发生的写入。只检查用户输入，也覆盖不了后来从文件读出的内容。这就是把检查放在不同位置的理由。

## 下载并运行这个边界

下载[Agent 机制示例包](/downloads/agent-examples/mechanisms.zip)。ZIP 根目录直接包含 `app.py`、共享 runtime、机制模块和依赖清单，解压时明确指定目标目录：

```sh
unzip mechanisms.zip -d mechanisms
cd mechanisms

source .venv/bin/activate
python -m pip install -r requirements.txt
python app.py --part guardrails
python -m unittest -v test_guardrails
```

Python 最低版本为 3.11。上面的 shell 和激活命令适用于 macOS/Linux；本次实际检查环境是 macOS arm64、Python 3.11.16，没有把它写成跨操作系统验证。

聚合应用实际输出先标明：

```text
fixture / 本地确定性机制验证；不调用模型服务
```

接着 `guardrails` 的 JSON 包含 `ok: true`、`authorized_tool_calls: 2`，以及十项为真的检查结果，例如 `unknown_operation_rejected`、`unapproved_write_rejected`、`tool_injection_blocked` 和 `approved_write_read_back`。同时明确输出 `detection_scope: "known-patterns-only"`、`is_os_sandbox: false`。

这些结果来自实际操作和断言。演示在自己的临时目录里建立合成笔记，拒绝未批准写入，再为一份固定草稿授予测试用批准；经公共循环完成读取与写入后，重新读回文件核对，最后清理目录。它没有实现真实确认界面，也没有调用模型服务。

## 只提供两项明确的工具

`GuardedTools(root)` 接收一个已经存在的工作区。模型只会得到下面两项工具：

| 工具 | 本例允许的范围 |
| --- | --- |
| `read_note(path)` | 读取 `notes/name.md` 中的 UTF-8 普通文件 |
| `write_draft(path, content)` | 写入 `drafts/name.md`，但完整操作必须先由宿主批准 |

`name` 只能以英文字母或数字开头，后续使用英文字母、数字、下划线和短横线。本例不支持嵌套目录、隐藏文件或其他扩展名；这是一项有意收窄的教学策略，不是通用文件管理器。

输入文本、文件内容与返回载荷各有 4096 字节的上限。文件返回成 JSON 时还要计入字段和转义字符，所以“文件不超过上限”本身不保证整个返回载荷也能通过。

每项工具都有 JSON Schema，列出必填字段、类型和大小，并拒绝额外参数。公共 runtime 在调用 handler 前验证一次，`dispatch()` 内部再独立验证一次。后者使直接调用公开 handler 时仍有检查，也避免把外层 schema 当成唯一限制。

没有 `execute_command`、`delete_file` 或 `approve_write` 工具。模型即使猜到这些名字，注册表与分发入口也不会执行它们。程序没有一个让调用方随意传入 `tool_fn` 的后门入口。

## 拒绝必须发生在副作用之前

`dispatch()` 按顺序处理：确认操作和参数，解析工作区路径，检查这项操作允许的目录，再处理内容与授权。绝对路径、父目录跳转和符号链接在文件读写前拒绝。

对写入，顺序更具体：先检查内容，再核对批准，检查计划返回的结果能否公开，最后才调用 `atomic_write_text()`。输出检查如果在这个位置拒绝，写入函数还没有执行。测试会直接观察该函数没有被调用，并检查文件不存在或旧内容保持原样。

读取则不同。程序必须先在允许路径读取内容，才能扫描里面的文字。命中后拒绝的是这份数据继续传给模型，不是声称“从未访问过文件”。因此可读笔记目录本身也应当按任务准备，不能把内容扫描当成读取秘密目录的授权。

到达 `dispatch()` 的调用会留下操作名和结果码，这份记录不复制完整参数、正文或命中的敏感内容。它产生的拒绝只包含如 `invalid-arguments`、`write-approval-required` 的错误码，不把被拒绝的原文放进说明。更早被公共 runtime 拒绝的未知工具或无效参数，由公共循环记录为工具失败。

## 批准完整操作，而不是让模型自己说批准

宿主可以在用户审阅具体目的地和新内容之后，调用：

```python
# 宿主集成片段：boundary 已由 GuardedTools(workspace) 创建，用户已审阅这份操作。
boundary.approve_write("drafts/result.md", "# 草稿\n\n已审阅的内容。\n")
```

这不是向模型开放的工具。批准记录同时绑定三个条件：目标路径、新内容的 SHA-256、批准时现有文件的摘要；目标不存在时也会记录这一事实。

之后模型改了内容、换了路径，或者文件被用户另行编辑，批准都会失配。一次提交尝试消费一次批准；如果写入报错，也不继续无限复用原批准。摘要用于核对本次批准对应哪一份内容，不证明内容本身安全，也不提供账号认证。

本例的 `demo()` 用宿主代码为固定合成草稿建立批准，目的是验证匹配和拒绝。真实界面或 CLI 应把用户明确批准接到这个方法，不能把测试夹具里的固定批准当作真实用户确认。

## 扫描命中以后，真的停止传递

示例用两组有限规则演示检查：

- 已知指令模式，例如 `ignore previous instructions`、`请忽略之前的规则`。
- 合成敏感标记 `DEMO_SECRET_...`，以及 `password=...`、`api_key=...` 等已列出的文字形式。

用户任务命中时，`run_guarded_agent()` 在调用模型之前返回 `input-denied`。测试使用没有任何响应的固定模型，确认它没有收到请求，也没有执行文件工具。

允许读取的笔记命中时，`read_note` 不返回原文，而是抛出安全结果码。公共 runtime 把这次工具调用记为失败。测试检查下一次模型请求里的 tool 消息，确认其中没有原始可疑指令或合成秘密；这里没有“原文照常返回，再追加一条安全提示”的分支。

![直接请求与工具资料中的提示注入路径](guardrails_prompt_injection.svg)

*图 2：图示区分直接输入与工具资料两条来源。本文实现的扫描只处理已知文字模式；即使扫描漏掉内容，后续工具仍受操作、路径与授权限制。*

这些规则可能漏掉改写、编码或拆开的秘密，也可能误拦截一段正常讨论提示注入的文章。测试命中的样本不代表检测了任意 Prompt Injection。增加模型分类器时，还要另外验证误报、漏报与失败策略；本例没有伪装成已经实现这一层。

## 最终回答的过滤，不能撤销已发生的操作

公共循环结束后，`run_guarded_agent()` 还会检查最终文本。命中同样的敏感或指令模式时，返回 `output-denied` 和固定的 `[output withheld]`，不向调用者交出原始回答或完整消息历史。

但如果一项写入已经独立通过检查并获得批准，随后最终回答被拒绝，文件仍然存在。测试专门保留这条路径，避免把“回答没有返回”误写成“所有动作都没有发生”。

因此要区分两种否决：工具提交前拒绝，可以阻止该次写入；最终回答拒绝，阻止的是这次文本继续返回。需要回滚或事务保证时，应为具体资源另行设计，本例没有实现通用撤销。

## 工作区边界与操作系统隔离分别做什么

本例能约束的是：模型经这套注册工具提出的读写请求。不可信文本不能把不存在的命令工具变出来，工具请求也不能通过多传参数或更换路径跳过检查。

它不能限制同一解释器里任意 Python 代码，也不防其他进程同时替换文件或目录。Python 的私有方法命名不是隔离机制，所以不应一边依赖这些工具限制，一边又向同一模型开放任意 Python 或 shell 执行。

[Python 的 subprocess 文档](https://docs.python.org/3.11/library/subprocess.html)把 `cwd` 描述为子进程的工作目录，`env` 是它的环境变量。修改这两项不会撤销进程已有的文件、网络和系统权限；命令首词允许列表和危险字符串匹配也没有建立隔离环境。

如果任务确实需要执行不可信程序，应在本模块之外配置并验收操作系统或虚拟化提供的隔离，具体检查文件可见范围、网络、权限和资源限制。这里没有启动、配置或验证容器、虚拟机，也不把“过滤后直接 subprocess”保留成一个叫沙箱的可执行示例。

## 真实产品中的 Guardrails 设计

产品中的权限配置可以帮助辨认确认和拒绝发生的位置，仍需区分权限提示与执行隔离。下面保留已核对的 Claude Code 例子。

### Claude Code 的权限模型

按[官方文档](https://code.claude.com/docs/en/permissions)（2026-10-17 核对），这里以手动确认的 default 模式举例，实际询问还受权限规则影响：

- 允许范围内的只读工具可直接执行；文件修改和多数命令需要确认。
- `.claude/settings.json` 可配置允许、询问和拒绝规则；切换模式也会改变询问范围。
- `--dangerously-skip-permissions` 绕过常规权限提示，本身不提供隔离。
- MCP 工具仍按配置判断，接入本身不等于额外隔离。

## 怎样验证不是只写了一段提示

本次在 macOS arm64、Python 3.11.16 上运行了 22 项标准库 unittest 检查，全部通过。它们使用真实临时文件和公共工具循环，模型响应由 `ScriptedModel` 固定，不调用模型服务。

| 检查 | 实际观察 |
| --- | --- |
| 未知操作、无效参数、越界路径 | 没有调用写入函数，越界文件保持原样；无效路径也不会进入读取函数 |
| 公开 handler 和公共循环 | 两条路径都调用同一个受检查的 `dispatch()` |
| 未批准或批准失配的写入 | 不创建新文件，不替换旧内容 |
| 内容或计划输出被拒绝 | 写入提交尚未发生 |
| 读取笔记命中已知模式 | 下一次模型请求没有收到被拒绝的原文 |
| 最终回答命中敏感模式 | 返回固定占位文本，不交出原回答 |
| 已批准写入后回答被拒绝 | 文件仍保留，未冒称已经回滚 |
| 聚合演示 | 重新读回已批准文件，并在结束后清理自己的临时目录 |

源码目录运行时，将公共 runtime 放进导入路径：

```sh
PYTHONPATH=../common python -m unittest -v test_guardrails
PYTHONPATH=../common python app.py --part guardrails
```

这些命令在 `examples/agents/mechanisms` 目录执行。下载包的共享 runtime 已在根目录，不需要设置 `PYTHONPATH`；包内也不重复运行公共 runtime 自己的测试。

用相同方式检查新的工具时，先说明它能影响哪些对象、哪些请求应被拒绝，再让拒绝用例观察真实结果。仅隐藏工具名称、追加风险提示或打印“已拦截”，都不能代替执行路径上实际停止的分支。

[Reflection](/agent/reflection-agent/)可以帮助模型重新审视回答，但本篇的准入条件由运行程序执行。已知模式检查、可信调用者提供的批准、固定路径范围，都有明确前提；这些本地机制不构成多租户安全平台，也没有证明抵抗所有提示注入。
