假设你接到一个 Bug：用户取消导出后，界面已经显示“已取消”，磁盘上却仍然出现了导出文件。要求也很明确：取消要停止后续写入，清理临时文件，正常导出不能受影响。

把这段需求交给模型，它可能马上给出一份合理的代码。要让这份代码在项目里生效，你还得找到导出入口，确认取消信号传到了哪里，检查文件写入方式，修改相关调用，再运行测试。任何一步产生的新信息，都可能改变最初的方案。

Coding Agent 把其中的读取、编辑和执行操作接入工具，让模型根据真实返回继续工作。**Harness 负责组织这个持续执行的过程**：准备模型输入，处理工具请求，保存会话状态，并在执行中接入权限和停止条件。本文用同一个假设任务解释这些职责，再到 DeepSeek Harness 的源码中寻找对应实现。

这篇开篇面向熟悉 Git、测试和大语言模型（Large Language Model，LLM）基本用法的开发者，不要求先运行 dsh。读完后，你应当能分清候选代码、工具结果与任务验收的关系，并知道下一步该沿哪些源码入口继续读。

## 补全能写出检查，却还不知道取消发生在哪里

假设你正在编辑文件写入函数，光标停在真正写入之前。补全可以根据附近的代码，建议先检查取消信号，再决定是否继续。对于已经选定位置、已经明确做法的局部修改，这种交互很直接。

困难在于，Bug 未必就在光标附近。假如导出任务经过“界面按钮 → 任务调度 → 文件写入”三层调用，写入函数拿到的信号可能从来没有被取消。也可能检查发生得太早：检查时任务正常，等异步操作结束，用户已经按下了取消按钮。局部代码即使写得符合语法，也未必碰到了故障原因。

[2021 年的代码生成研究](https://arxiv.org/abs/2107.03374)使用 HumanEval 检查根据函数描述生成的实现能否通过测试。这个任务说明了函数级代码生成如何评估，但没有要求系统在一个现有仓库里追踪取消信号、协调多处调用和准备项目环境。[^humaneval]

因此，使用补全时，开发者通常已经承担了问题定位和修改范围的判断。模型给出的候选实现，还要放进项目的接口与约束中检查。这里讨论的是以局部建议为中心的交互；具体编辑器还可能检索其他文件，不能用“补全”这个名字断定它只看光标附近。

## 对话能讨论整个方案，工作区仍需要有人接上

你也可以把问题描述、任务调度代码和文件写入代码发给对话助手。模型据此提出一个跨文件方案：把取消信号沿调用传下去，在合适的位置检查，并在退出路径清理临时文件。

这时，交互单位已经扩大为一个问题。你可以追问“正常导出会不会受影响”，也可以贴出编译错误，让模型修正接口。只要背景足够，对话就能帮助梳理方案，不必局限在一小段补全建议里。

不过，在只有文本输入输出的对话中，工作区和对话之间仍需要人工搬运。你复制代码、应用补丁、执行测试，再把报错贴回来。若漏掉了一个调用者，模型就缺少那处接口约束；若中途改过文件却没有更新对话，它接着分析的仍是旧内容。

以这个 Bug 为例，模型可能认为“取消后不再生成最终文件”已经满足要求，而项目还要求删除临时文件。把测试失败贴回对话以后，它才能得到这一条新增证据。开发者在这里同时承担了信息选择和执行反馈的工作。

这种方式适合讨论方案、解释报错，也适合需要逐步人工控制的修改。仓库任务变长以后，反复搬运信息就成了需要处理的环节。

## Agent 把执行结果接回下一次模型请求

给模型提供读取文件、编辑文件和执行命令的工具后，它可以提出具体动作，由运行系统执行，再根据返回结果继续判断。在我们的假设任务中，一个可能的过程是：

1. 搜索导出入口，读取任务调度和文件写入实现。
2. 检查取消信号的传递，查看正常导出与取消路径的已有测试。
3. 修改相关调用，运行针对这条行为的检查。
4. 如果检查发现临时文件没有清理，读取错误信息，再调整退出路径。

这些步骤只是机制示例，并非 dsh 的实际运行记录。它们也不要求按固定脚本发生：工具可能被拒绝，命令可能失败，新的信息可能让原来的方案失效。

[ReAct](https://arxiv.org/abs/2210.03629)研究了推理与外部行动交替进行的方式，行动得到的观察可以影响后续决策。[SWE-agent](https://arxiv.org/abs/2405.15793)则把仓库导航、文件编辑和程序执行组织成面向软件工程任务的接口。这些工作提供了理解反馈循环的依据；具体系统仍要决定开放哪些工具，以及怎样执行它们。[^react][^sweagent]

模型输出的一条工具调用，还只是一个待执行的请求。读取工具需要访问真实文件，命令工具需要启动进程并捕获输出，运行系统也可能因为权限、取消或参数问题拒绝执行。模型能用到的观察，取决于工具实际返回了什么，以及这些内容有没有进入后续请求。

三种交互可以在同一产品里共存。下面比较的是它们各自的工作方式，不能据此给产品划定永久边界。

| 比较项 | 代码补全 | 纯文本对话助手 | 使用仓库工具的 Coding Agent |
|---|---|---|---|
| 一次交互围绕什么 | 编辑位置与候选实现 | 问题、方案与补丁 | 任务及连续动作 |
| 谁把信息带进模型输入 | 编辑器提供上下文，开发者选择位置 | 开发者提供材料 | 运行系统组装输入，模型可请求工具补充信息 |
| 谁操作工作区 | 开发者接受或修改建议 | 开发者应用方案 | 工具在获准范围内执行 |
| 新报错怎样回来 | 开发者查看，再调整代码 | 开发者贴入对话 | 工具结果可进入后续模型请求 |
| 怎样确认完成 | 项目检查与维护者验收 | 项目检查与维护者验收 | 项目检查与维护者验收，另需检查执行过程 |

## “仓库级”增加的是约束与依赖范围

回到取消导出的任务。要判断修复是否成立，需要同时知道取消按钮调用了什么、任务对象怎样保存信号、写入函数如何退出、临时文件由谁清理，以及测试怎样模拟这些行为。分散在不同文件中的事实共同限制了方案。

“仓库级”描述的就是这种任务范围。Agent 需要按问题持续获取相关实现和项目规则，也要协调修改带来的接口影响。一次把所有文件塞进模型输入，并不能替代这些判断；获得整个目录的读取权限，也不代表获得发布或外部操作的授权。

[SWE-bench](https://arxiv.org/abs/2310.06770)将真实 GitHub issue 与对应仓库组织成评测任务，要求系统在既有代码库中完成修改。这与给定一个函数描述再生成实现的评测，考察了不同的工作范围。[^swebench] 本文借此区分任务类型，不比较不同论文的分数，也不据此推断 dsh 的任务成功率。

对我们的例子，合理的验收至少要检查取消后的最终文件、临时文件清理和正常导出。若修改了公共接口，还需要检查其他调用者。把这些条件写清楚以后，Agent 才有明确的观察目标；否则，“界面显示已取消”和“文件操作已经停止”很容易被混为一件事。

## Harness 要把哪些事情组织起来

本文把模型周围负责运行这些动作的软件层称为 Harness。这个定义覆盖一组职责，具体实现可以放在一个进程里，也可以拆成插件和服务。对于取消导出的修复，最需要关注以下几处。

### 模型看到的是怎样一份仓库事实

文件内容、项目说明、用户要求、历史消息和工具定义，要经过选择与组装才能进入一次模型请求。Harness 需要决定取哪些内容、保留到什么时候，以及如何处理超出上下文容量的结果。

如果读到的是旧的写入函数，后续分析就可能建立在旧接口上。如果一段测试输出被截断，模型也可能看不到真正的失败原因。研究上下文机制时，应追踪“哪份内容进入了哪次请求”，而不能只检查界面上是否出现过它。

### 工具调用怎样变成一次受约束的操作

工具接口要把模型提出的名字和参数，转换成实际的文件访问或进程操作。执行前可能需要校验、策略判断和审批；执行中还涉及超时、取消和输出处理。运行系统最后要把结果送回执行循环。

例如，允许运行一个聚焦测试，与允许命令访问网络或写入仓库外的目录，是不同的授权范围。工具已经注册，只说明系统存在这个入口；实际能做什么，还取决于执行策略和底层环境。检查权限时，要找到具体的强制执行位置。

### 多次动作之间怎样保留过程

读取了哪些文件、模型提出了什么调用、工具返回了什么、任务在哪一步停止，这些信息决定了后续请求如何构造，也决定了开发者能否解释一次失败。会话记录因此承担了比聊天展示更多的工作。

记录过程与撤销操作需要分别实现。即使日志完整保存了“写入某文件”的动作，文件也不会因此自动恢复；一条已经发出的外部请求，同样需要独立考虑其副作用和补救方式。

### 运行何时停止，结果怎样交给人检查

工具返回以后，运行系统需要决定是否继续请求模型，还是因为取消、限制或其他条件结束。最后的回复应当让开发者知道修改了什么、哪些检查实际执行过、还有哪些条件没有验证。

这些记录有助于验收，验收标准仍来自任务和项目。对于取消导出的 Bug，只看到模型说“已经修好”，无法判断取消后磁盘上有没有残留文件；只看到测试命令正常退出，也还需要确认那组测试覆盖了要求。

## 到 DeepSeek Harness 中寻找这些职责

DeepSeek Harness，简称 `dsh`，在固定版本的 [README](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/README.md)中将自己定位为基于 Cordis、采用 “everything-is-a-plugin” 架构的开源 Agent Harness，并标明处于 developer preview，可能发生不兼容变化。[^readme]

Cordis 在这里负责组合插件，以及提供服务、事件和生命周期管理。理解插件时，可以先关注两件事：它提供了什么能力，其他代码怎样取得或调用这项能力。[架构文档](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/docs/architecture.md)把模型适配器、工具、Agent 执行与会话等职责放到了可分别阅读的入口中。[^architecture]

| 本文提出的问题 | 固定版本的阅读入口 | 先观察什么 |
|---|---|---|
| 输入怎样参与后续执行 | [Agent 执行循环](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/packages/core/agent-loop/src/agent.ts) | 输入接收、请求准备、继续与停止 |
| 项目材料怎样进入请求 | [System Prompt 组装](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/packages/core/system-prompt/src/index.ts) | 上下文来源、组装时机与扩展位置 |
| 工具请求怎样获准并执行 | [工具运行时](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/packages/core/tools/src/index.ts#L1499) | 执行前策略、审批、拒绝与调用 |
| 模型历史怎样从记录得到 | [Session 的 `deriveMessages()`](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/packages/core/session/src/index.ts#L984) | 会话事件如何派生为模型消息 |

两个具体实现能先把这些职责连起来。

工具运行时的 `prepareExecution()` 先构造调用上下文、检查取消，再经过 `tools/pre-execute`。需要询问的决定会进入审批处理；拒绝或取消可以形成结果并结束这条执行路径，获准且通过后续检查的调用才进入分派。由此可见，模型提出工具调用之后，仍有运行系统负责的执行边界。[^tools]

Session 的 `deriveMessages()` 则从当前会话表面中产生消息的事件派生模型历史。这里的“会话表面”可以先理解为当前参与消息构造的有序记录；日志里还可能有轮次边界等其他事件。研究模型看到什么，需要沿消息派生与请求构造继续追踪。[^session]

这套拆分为源码阅读提供了清楚的问题入口。它的代价也会在后续阅读中出现：理解一次行为，往往需要同时找到服务接口、提供者、消费方和事件处理函数。插件之间的组合关系值得研究，实际效果还要放回具体任务中验证。

安全边界尤其需要单独检查。Cordis 的服务作用域与操作系统的文件、进程隔离承担不同职责；会话持久化也没有自动撤销工作区副作用的含义。项目的 [SAFETY.md](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/SAFETY.md)明确提醒，沙箱、审批和权限控制可以降低风险，但不能保证隔离或防止损害，获准访问的资源仍可能受到影响。[^safety]

## 怎样判断这个修复真的完成了

一个 Agent 可以顺利跑完执行循环，交付的修改仍然不满足需求。对于取消导出的例子，几种观察分别回答不同的问题：

| 观察到的结果 | 它回答了什么 | 还需要检查什么 |
|---|---|---|
| 模型生成了修改方案 | 有了一份候选做法 | 是否符合真实调用关系 |
| 编辑工具返回成功 | 工具报告完成了编辑 | 差异是否正确、是否影响其他路径 |
| 聚焦测试通过 | 这组断言在当前环境下成立 | 是否覆盖取消后的文件状态与正常导出 |
| 维护者接受修改 | 修改在已说明的条件下符合项目要求 | 发布与外部影响是否属于本次授权 |

因此，仓库级 Agent 的交付应当包含可检查的修改与实际执行的验证。测试选择、环境限制和未完成项会影响验收，应该随结果一起保留。遇到失败时，也需要能分清：模型选错了方案，工具没有获得足够权限，执行环境缺少依赖，还是测试本身没有覆盖目标行为。

本系列会从这些具体问题进入源码。[第二篇：一次用户请求如何经过整个 dsh 系统](/articles/deepseek-harness-request-lifecycle/)已经发布，沿输入、模型、工具、会话记录和输出追踪完整链路。先读通一条请求，再分别展开上下文、工具、安全和恢复，前面的职责就能对应到真实调用。
