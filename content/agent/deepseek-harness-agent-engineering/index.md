## 这篇文章要解决什么问题

模型能够生成代码以后，开发者还需要把代码放入项目、补齐依赖、运行检查，再把错误交给模型。Coding Agent 将这些操作接入工具，模型可以读取文件、修改代码、执行命令，并根据返回结果继续工作。随之而来的问题是：谁组织上下文，谁保存过程，谁决定一次操作能否执行，又由谁确认任务真正完成？

这是 [DeepSeek Harness 源码解析系列](/series/deepseek-harness/)的开篇。本文面向了解 Git、测试和大语言模型（Large Language Model，LLM）基本概念的开发者，先解释代码补全、对话助手与仓库级 Agent 的区别，再说明 Harness 的职责和本系列的研究范围。后续源码文章会用到 TypeScript 与 Node.js；本篇不要求读者先运行 dsh。

## 先给结论

Coding Agent 需要一个持续组织输入、执行动作、接收结果和保存状态的运行系统。本文用 Harness 指代模型周围承担这些职责的软件层。模型负责根据输入生成响应或提出工具调用；Harness 负责把这些请求放进有状态、可观察、受权限约束的执行过程。

仓库任务还依赖模型之外的事实：当前文件、依赖版本、架构约定、测试入口和维护者的验收标准。把工具交给模型以后，这些事实需要进入请求构造和执行流程，工具产生的结果也需要接受外部检查。测试、代码审查和发布责任因此继续属于整个开发流程。

DeepSeek Harness 将模型、工具、会话和外围能力组织成 Cordis 插件，适合用来逐项研究这些职责如何落实。本系列会沿着实际调用链解释实现，再展开服务、事件、配置、状态和失败路径。项目定位与源码结构提供实现证据，模型完成任务的成功率、成本和安全效果仍需要另外测量。

## 四类开发助手各自负责什么

先按交互方式和执行权限区分几个容易混用的概念。

| 对象 | 主要输入 | 产生的结果或动作 | 开发者仍需负责的工作 |
|---|---|---|---|
| 代码补全 | 光标附近代码、编辑器缓冲区与部分文件上下文 | 代码建议 | 接受或修改建议，运行检查，确认意图 |
| 对话式代码助手 | 用户问题、对话历史与提供的代码 | 解释、方案、代码片段或补丁文本 | 放回真实项目，确认依赖与版本，执行验证 |
| Coding Agent | 任务、模型请求、工具定义、工作区与工具结果 | 读取、编辑、执行命令，并根据结果继续行动 | 授权范围，审核修改，判断外部影响 |
| 仓库级 Agent 工程 | 以上内容，以及项目约束、持久状态与验收规则 | 在项目环境中执行多步任务，保留过程与结果 | 维护事实来源，定义验收，决定是否接受和发布 |

“仓库级”描述任务依赖的范围。一次修复可能牵涉多个文件、构建配置、测试和兼容性要求，Agent 需要按任务持续获取相关信息；这个词不表示模型一次读完整个仓库，也不表示它拥有全部权限。

这几种交互方式可以共存。开发者可能在同一天用补全写一个函数，用对话解释错误，再让 Agent 修改几个相关文件。下面的演进路径关注每种方式增加了哪些能力，以及相应的工程要求。

## 从工具辅助到执行仓库任务

### 早期程序综合与开发工具

Manna 和 Waldinger 的 [Toward automatic program synthesis](https://doi.org/10.1145/362566.362568) 研究如何从规格和证明中构造程序。开发者提供形式化性质，系统据此推导实现。这条路线将一部分手工推导交给工具，同时要求规格足够精确，并依赖可处理的证明与搜索过程。

集成开发环境（Integrated Development Environment，IDE）、计算机辅助软件工程（Computer-Aided Software Engineering，CASE）、静态分析和重构工具，则更多地处理导航、诊断、构建与机械编辑。它们可以依据语法树和类型信息执行变换，帮助开发者完成已知操作。它们属于传统工程基础设施，不能因为参与了自动化就全部归为 AI。

Brooks 在 [No Silver Bullet](https://doi.org/10.1109/MC.1987.1663532) 中区分软件工程的本质复杂度与偶然复杂度。这个区分仍有助于理解后来的工具：减少代码书写、查找和执行命令的劳动之后，需求、设计和协作问题仍然需要处理。

### 代码库成为可学习的数据

Hindle 等人的 [On the naturalness of software](https://doi.org/10.1109/ICSE.2012.6227135) 指出，代码包含可被统计语言模型捕捉的重复模式。[Big Code 与软件自然性综述](https://doi.org/10.1145/3212695)进一步整理了代码搜索、表示、生成和程序分析中的机器学习方法。

模型可以从大量代码中学习惯用法和相似结构，减少开发者手写检索规则的工作。不过，片段相似不保证行为相同。调用顺序、配置、权限和依赖可能改变其含义；训练语料与评测切分也会影响测量结果。

### 代码模型与编辑器补全

[CodeBERT](https://arxiv.org/abs/2002.08155) 将自然语言与代码纳入预训练，研究代码搜索和文档生成。[Codex 论文](https://arxiv.org/abs/2107.03374)讨论代码生成，并用 HumanEval 检查函数级功能正确性。GitHub 的 [Copilot 技术预览说明](https://github.blog/news-insights/product-news/introducing-github-copilot-ai-pair-programmer/)则把这一能力放进编辑器，根据当前代码提供整行或函数建议。

开发者由此可以从函数签名、注释或局部代码获得候选实现。模型降低了部分代码书写成本，结果仍需要编译、测试和审查。函数级评测也无法代替跨文件、跨配置的仓库任务验证。

### 对话助手扩大了问题范围

自然语言对话让开发者可以询问错误原因、比较方案、补充需求或要求生成补丁。一次交互的中心从光标位置扩大到一个问题，开发者也可以逐轮补充背景。

对话历史保存的是用户提供的信息。它不会自动更新到当前工作区状态，也无法确认没有展示的配置和约束。生成的补丁需要放回真实仓库，才能检查接口、依赖、测试和项目约定。

### Coding Agent 建立了行动与观察的循环

[ReAct](https://arxiv.org/abs/2210.03629) 研究推理与外部行动交替进行的方式：行动获取信息，返回的观察用于继续决策。[SWE-agent](https://arxiv.org/abs/2405.15793) 将文件编辑、仓库导航和程序执行组织成面向 Agent 的接口。

在这种交互中，模型可以提出“读取这个文件”“运行这条命令”等动作，并收到工具结果。开发者逐次搬运代码、执行命令和粘贴错误的工作，部分进入了 Agent 的执行循环。

工具也带来新的要求：路径和命令权限、输出大小、超时、取消、并发、状态保存和结束条件。如果命令可以修改外部状态，错误决策的影响就会扩大；如果工具结果被截断或执行没有终止，模型还可能重复尝试并继续消耗资源。

[SWE-bench](https://arxiv.org/abs/2310.06770) 将真实 issue 和仓库修改组织成评测任务，体现了多文件协调与执行环境的重要性。[OpenHands](https://arxiv.org/abs/2407.16741)则把代码编辑、命令行、网页、沙箱和评测放到同一平台。评测结论仍绑定具体任务、模型和判定方法，不能直接外推到 dsh。

## 为什么仓库任务需要 Harness

考虑一个假设任务：“为接口增加参数校验，并补上回归测试。”这不是本文运行过的实验，只用来说明执行过程需要哪些信息。

Agent 首先要定位接口、调用方、测试与项目规则。模型提出修改后，工具需要检查路径和执行权限，再返回实际操作结果。测试失败时，下一次模型请求应包含足够的错误信息；中断后，开发者还要知道哪些文件已经改变，哪些命令执行过，以及接下来能否继续。

可以用下面这条抽象流程理解这些职责。它不代表 dsh 的具体事件顺序，后续文章会用源码还原真实链路。

```text
任务与项目约束
    ↓
组织模型输入：指令、相关文件、历史与工具定义
    ↓
模型生成响应或提出工具调用
    ↓
检查执行策略 → 执行工具 → 记录结果
    ↓
结果进入下一次模型请求，直到满足结束条件
    ↓
检查文件、测试与最终修改，由维护者决定是否接受
```

这个流程包含几个需要独立实现的部分。

| 职责 | 需要回答的问题 |
|---|---|
| 上下文组织 | 这次请求看到了哪些指令、文件、历史和工具？ |
| 工具执行 | 参数是否有效，动作是否允许，异常如何返回？ |
| 状态与日志 | 已经发生了什么，哪些信息可以恢复或重建？ |
| 生命周期 | 何时继续、停止、取消或重试，如何清理资源？ |
| 外部验证 | 文件和程序实际变成什么状态，满足了哪些验收要求？ |

文档、测试、持续集成（Continuous Integration，CI）和代码审查参与的是不同环节。文档提供项目事实与约束；测试检查可执行的断言；CI 在提交或发布路径重复检查；代码审查判断设计、兼容性、权限与业务语义。它们共同提供反馈，维护者需要明确各自能证明什么。

## DeepSeek Harness 在这里承担什么

[固定版本 README](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/README.md) 将 DeepSeek Harness 定义为 DeepSeek AI 开发的开源 agent harness，采用“everything-is-a-plugin”架构，由 Cordis 支持。该版本同时标为 developer preview，并明确提示兼容性可能破坏。

插件架构为研究提供了可以逐项定位的实现边界。核心模块组织 Agent、Session、Prompt 和工具，外围模块提供模型适配、文件系统、Shell、审批、上下文、持久化与界面。我们可以先追踪一次请求，再沿着它经过的服务和事件展开阅读，参照[架构文档](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/docs/architecture.md)复核职责。

需要分别检查插件组合与安全隔离。一个插件可以注册服务或工具，但实际文件、进程和网络权限由加载的实现、执行策略和运行环境决定。会话恢复也只说明相应状态如何继续使用；工作区文件或外部操作能否撤销，需要查看独立的恢复机制。

本系列围绕这些可核对的实现展开。对 dsh 的结构分析，不能直接推出它完成真实仓库任务的成功率、成本、延迟或安全保证。

## 总结

- 代码补全、对话助手与 Coding Agent 改变了开发者的交互方式和执行流程，仓库事实与验证责任也随之进入系统设计。
- Harness 组织模型周围的上下文、工具、状态与生命周期，让多步行动有可检查的执行过程。
- 模型输出、工具返回、测试结果和维护者判断提供不同的证据，需要分别记录其适用范围。
- DeepSeek Harness 的插件与事件实现将作为本系列的研究对象，接下来先还原一次请求的完整链路。
