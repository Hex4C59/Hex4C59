判断一层封装是否值得保留，需要把它放回具体需求：它替调用者承担了什么，调用者仍需知道什么，某项变化会传播到哪里。代码能运行，为这些判断提供了一部分证据；要作出选择，还需要比较另一种满足相同需求的实现。

本系列面向已经能读写简单 JavaScript、开始维护完整功能的开发者。如果你能理解对象、函数和条件分支，就可以从这里开始。前几篇用短小的 JavaScript 模块讨论抽象、契约与间接调用，之后按需要引入 TypeScript 和本地任务列表。完整安排见[系列目录](/articles/software-design/)。

读完这篇导读，你应能沿着一次调用说明返回值从哪里来，并把一句“这样设计更好”拆成可以检查的问题。

## 先说清这段代码做了什么

假设有一个演示应用，它的版本信息保存在对象里。下面是一个完整例子：

```js
const appInfo = {
  version: "1.0.0",
  internalBuildTag: "demo-build",
};

function getAppVersion() {
  return { app: appInfo.version };
}

const result = getAppVersion();
console.log(result.app);
```

`appInfo` 是一个对象，`version` 和 `internalBuildTag` 是它的属性。`appInfo.version` 读取 `version` 的值，当前是字符串 `"1.0.0"`。

`getAppVersion` 定义了一个没有参数的函数。执行 `getAppVersion()` 时，函数读取版本值，创建一个带有 `app` 属性的新对象，再把对象返回给调用处。`result` 接住返回值，所以最后一行输出 `1.0.0`。

这个函数没有把 `internalBuildTag` 放进结果。由此可以观察到“返回字段经过了选择”。至于为什么选择这些字段，需要需求或设计说明提供依据。仅凭代码，还不能判断内部构建标记是否敏感、是否必须隐藏，也不能断言这个函数让整个项目更容易维护。

## 函数值与函数调用要分开读

下面的片段接在前一个例子后面运行：

```js
const query = getAppVersion;
const first = query();
const second = query();

console.log(first.app);
console.log(first === second);
```

`const query = getAppVersion` 把函数值交给另一个名称。这里没有括号，所以这一行没有执行查询。`query()` 才会调用函数，与 `getAppVersion()` 执行同一段函数体。

两次调用都返回包含 `app: "1.0.0"` 的对象，但每次执行对象字面量都会创建一个新对象。这里的 `===` 比较两次返回值是否指向同一个对象，所以第二行输出 `false`。字段值相同与对象身份相同，是两个需要分别检查的性质。

可以下载[导读的完整检查文件](reading.mjs)，保存为 `reading.mjs`，在保存它的目录运行：

```sh
node --version
node reading.mjs
```

在 2026-10-14 的 macOS arm64、Node.js v25.9.0 环境中，输出为：

```text
1.0.0
false
```

文件使用 Node.js 内置断言，断言不成立会以错误结束。它只检查这组示例的字段值和对象身份，没有检查实际应用的版本来源。

## 再问调用者需要知道什么

现在有两种取得版本的写法。以下是比较片段，依赖前面定义的对象和函数：

```js
const versionA = appInfo.version;
const versionB = getAppVersion().app;
```

第一种要求调用者知道内部对象名和属性名。第二种要求调用者知道函数名、返回结果中的 `app` 字段，以及调用会立即返回普通对象。第二种写法增加了一个函数，但是否减少了调用者需要掌握的细节，要看它后面承担了多少工作。

如果应用只有一处显示版本，数据结构也很稳定，直接访问可能已经足够。假如多个调用者分别处理不同的数据来源，查询函数又把这些来源和转换集中到一起，比较结果就可能改变。[第 01 篇](/articles/software-design-01-abstraction/)会把这些情况拆开运行。

在这个系列里，**接口**指调用者通过什么名称、参数和结果使用一项能力；**抽象**指调用者借助这样的表示处理问题，可以暂时不关心其中一部分实现细节。我们会继续问：具体允许忽略哪些细节，又留下了哪些必须理解的约定？

## 用一项变化检验设计理由

假设原来的 `appInfo.version` 改成了 `appInfo.release.version`，而关于页仍应显示同一个版本。这是内部数据表示变化，用户需要的结果暂时没有变化。

直接访问的调用者需要调整属性路径。通过函数查询的调用者能否保持原样，要检查函数是否继续返回原来的 `app` 字段，是否仍然同步返回，以及调用者是否还在别处直接读取内部对象。函数名相同，并不能保证这些约定保持不变。

我们由此可以写出一句带范围的判断：“在版本字段和同步返回保持不变、调用者只使用查询结果的前提下，可以把内部属性路径的调整放进查询函数。”接着就能用修改前后的例子检查这些条件。

《How to Design Programs》第 2 版[第 3.1 节](https://htdp.org/2024-11-6/Book/part_one.html)把数据描述、函数目的、输入输出示例与测试纳入函数设计过程。这为这里的阅读方法提供了一个起点：先写清函数应该完成什么，再判断当前实现是否满足它。本系列采用原创 JavaScript 案例，具体语言行为另行核对。

## 读一篇时留下什么

对每个案例，试着留下能够让别人复核的材料：需求和约束、你比较过的两种实现、一次具体变化，以及运行或调用分析得到的结果。如果你认为一层封装值得保留，再补一句它承担的职责；如果你选择删除它，说明什么新需求出现时会重新考虑。

例如，对开头的函数可以先写下：

> 当前只需要取得应用版本。查询函数选择了一个返回字段，并创建新对象。它能否隔离数据来源变化，还需检查导出方式和实际调用者；如果只是把一次属性读取换成一次函数调用，当前收益可能很小。

这段说明包含已观察到的行为、尚未检查的条件和选择所依据的需求。带着这些问题进入[第 01 篇：抽象的收益与代价](/articles/software-design-01-abstraction/)，比较三种方案在同一项变化下的表现。
