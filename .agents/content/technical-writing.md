# Technical writing guide

本文件规定 `content/` 下技术文章的写作和证据要求，其中的易读性规则适用于所有博客正文。专栏的 front matter 和文章骨架由对应模板或专项指南负责。

## Section and series

新建文章、规划或续写系列、调整归属时，先按[内容归类规则](section-routing.md)确定主题、来源与系列关系，再安排提纲和 front matter。新文章默认使用 `content/articles/`；已发布文章保留目录与网址。

## Audience and scope

- 用户未指定时，技术解释默认面向会写简单代码、但不熟悉当前项目或框架的读者；非技术文章面向对题材感兴趣、没有专业背景的读者。用户指定读者时按其要求调整。
- 文章开头明确目标读者、必要的前置知识、要解决的问题、文章范围和可观察结果。开头与主要结论先用日常语言说明问题和结果，再进入实现细节。
- 标题直接说明主题或问题，避免只有“深入理解”“全面解析”一类无法判断内容的标题。列出前置知识后，仍要补足理解当前结论所必需的背景。

## Readability

本节适用于博客写作、续写、改写、润色、翻译和系列规划。规划阶段确定读者与解释顺序；有正文时执行以下要求和交付前理解检查。翻译保留原文的事实、条件与作者语气，必要的补充解释与原文内容明确区分。

### 解释顺序与术语

- 解释机制时，先交代具体对象、条件、动作与结果，再介绍源码或理论中的名称。需要时用一个小例子走通输入、处理和输出，再展开其他情况；按题目安排结构，不强制使用故事开头或问句标题。
- 陌生术语首次出现时，说明它在当前场景中做什么。缩写同时给出全称；中文译名、英文全称和术语表都不能代替职责与行为的解释。解释又引入陌生术语时，补上读者理解所需的说明。
- 保留准确的函数名、配置项、类型、命令和必要术语，保持同一对象的叫法一致。根据当前实现说明含义，不按字面把不同框架中的同名概念当成同一种东西。
- 用具体主语和动词说明行为。遇到“能力组合”“承载关系”“状态收敛”“持久谱系”等表达，检查是否交代了具体对象和操作；把省略的动作写出来，不建立全站禁词或机械替换表。
- 一句话依赖多个尚未解释的概念时，拆开并补足前提。可以为解释必要背景增加篇幅；删除重复铺垫，保留帮助读者理解因果关系的内容。
- 先让读者理解一个完整过程，再展开复杂分支。会改变当前结论的条件和失败情况，放在对应解释附近；开头保留必要的版本范围，完整 commit、机器环境、依赖和验证命令集中到来源与复现说明，并保留相关判断的依据。
- 图中节点说明具体主体或职责，箭头说明动作或传递的内容；需要查源码时，在次要标注中保留对应标识符。

例如，在对应语境中，“保存 Session 的持久谱系”应解释为“记录这段会话从哪段会话派生而来”，并说明这份记录影响什么。源码中的字段名保持不变；这种改写只解释原文支持的行为。

### 交付前理解检查

初稿后单独做一次理解检查，再完成套话与修辞检查；按目标读者的知识范围审视本次新增或修改的主要解释。检查每个主要机制能否从正文中回答：

1. 这一节解决什么具体问题？
2. 谁在什么条件下，对什么做了什么，为什么得到这个结果？
3. 换一个输入、调用方式或使用条件，结果会怎样？正文是否提供了作出判断所需的前提？

发现术语只解释了名称、指代不清、关键步骤跳过或例子不足时，先补足或重写对应段落，再交付。复述几个术语、缩短句子或减少术语数量，不能单独作为通过依据。

作者或 Agent 可以完成这次自查；记录时明确区分自查、模型模拟读者与真实读者反馈。只有实际开展了读者测试，才能报告测试结果。自动统计可标记候选问题，不能用词频、句长或英文阅读分数证明中文文章易懂。

在已有内部记录或交付说明中简述检查范围、发现的问题与修改结果。调研依据和逐段改写示例见[博客易读性调研](../../docs/research/blog-readability-2026-10-17.md)；本节是执行规则的统一入口。

## Structure and argument

- 先给结论，再说明问题、背景、关键概念、系统结构、实现过程、验证证据、限制和延伸阅读。
- 每个段落只承载一个主要观点，每个标题只服务于一个明确目的。
- 教程按前置条件和操作顺序组织；解释性文章按概念依赖和证据组织；参考性内容不要伪装成故事。
- 区分仓库中可以直接观察到的事实、实验或 benchmark 的测量结果、设计理由和作者判断。

## Evidence and reproduction

- 涉及性能、成本、延迟、准确率或模型能力时，说明版本、环境、输入、方法、样本或数据集和结果；不能用“明显更好”“效果很好”替代证据。
- 外部资料优先引用一手来源，并在快速变化的资料旁标注发布日期或访问日期。
- 代码示例必须服务于文章论点，并尽量通过真实项目入口验证。说明运行时、依赖、工作目录、完整命令、必要 import、预期输出和已知失败条件。
- 伪代码、删节代码和不可直接运行的片段必须显式标注；示例不能包含 API key、token、个人信息、私有路径或不安全默认配置。

## Accessibility and safety

- 图片和流程图提供能传达信息的 alt 文本；图示不能只依赖颜色区分状态，并在正文或图注中说明读者应观察的结论。
- 链接文字要描述目标，不使用孤立的“点击这里”。截图、日志和配置先脱敏，再发布；引用的图表、代码和文字要符合原始资料的许可证要求。
- 主动说明权限、文件系统、网络、沙箱、成本、延迟、兼容性和失败恢复等重要限制。
- 涉及安全机制时说明威胁模型、保护范围和未覆盖的情况，避免把“默认配置”写成安全保证。
