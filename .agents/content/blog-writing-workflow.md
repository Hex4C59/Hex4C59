# 博客写作工作流

创建日期：2026-10-14

适用于博客正文写作、改写、润色、翻译与系列规划。由根 `AGENTS.md` 路由进入；配图和内部规则维护按下表选择分支。具体写作要求保留在各 skill 与专项规范中，本文件规定何时使用、先后关系和完成条件。

## 先选择任务分支

按用户允许修改的范围选择流程。一次任务包含多种工作时，组合对应分支。

| 当前任务 | 执行顺序 |
| --- | --- |
| 原创解释、方案比较、实践教程、研究综述；或重建已有文章的论证 | 资料与论证：`research-explainer`；正文：`humanizer`；需要配图时：`diagram-design`；最后验证 |
| 只润色已有中文正文，保留事实、观点与结构 | `humanizer-zh`；核对原意、限定与受保护内容 |
| 忠实翻译、按给定材料整理或撰写个人随笔 | 源文或用户材料 → `humanizer`；需要新增外部事实或研究分析时，再执行 `research-explainer` 的相关流程 |
| 规划原创解释或教程系列 | 栏目与系列规则 → `research-explainer` → `humanizer`；交付篇目、论证范围、来源与状态 |
| 只修改分类、系列关系、front matter 或链接 | 栏目与系列规则及相关站点检查；正文发生修改时再进入对应写作分支 |
| 只创建或修改博客配图 | `diagram-design`；核对图文、来源与资源引用 |
| 编写或维护 Agent 指令、skill 与内部流程规则 | `writing-for-agents` → 其要求的 `humanizer`；核对规则、引用与完成标准 |

涉及正文或系列规划的所有分支，开始前读取并执行[易读性规则](technical-writing.md#readability)。正文完成后按该节做理解检查，再完成套话与修辞检查；已有 skill 的表达检查不能替代这一项。只做规划时落实读者与解释顺序；只改元数据、配图或内部规则时按对应分支检查。

用户明确指定 skill 或编辑范围时按其要求执行。中文润色不默认附加扩写和补充论据；在获准段落中补足必要解释，事实或编辑范围存在缺口时单独说明。

## 定位并执行 skill

- 项目内入口：[humanizer](../skills/humanizer/SKILL.md)、[humanizer-zh](../skills/humanizer-zh/SKILL.md)、[diagram-design](../skills/diagram-design/SKILL.md)、[writing-for-agents](../skills/writing-for-agents/SKILL.md)。
- `research-explainer` 先检查项目内同名 skill；不存在时从当前会话的可用技能清单取得实际路径，读取并执行。其他本地入口缺失时，也检查当前清单中的同名技能。仓库文档不保存个人绝对路径。
- 首次使用时告知用户技能名称与用途，读取 `SKILL.md` 及其中要求必读的参考文件，再完成对应步骤。同一任务已读取且仍有效的内容可以继续使用。
- 记录时区分“已阅读”和“已执行”。执行意味着完成该 skill 对本任务要求的步骤与检查；只读描述或借用其中一句建议不能记为已执行。
- 上游 skill 已要求并完成的下游检查计入本次执行。例如 `writing-for-agents` 内含 `humanizer`，无需再重复整套流程。纯中文润色默认选择 `humanizer-zh`；正文已按 `humanizer` 完成表达检查时，不自动再叠加一次。
- 必需技能或其必读依赖不可用时，明确说明缺失项和受影响步骤；交付状态保留该缺口，不能报告为完整执行。

## 原创技术文章的执行步骤

### 1. 明确范围与适用规范

检查工作区和相关文件，保留已有修改。按[栏目与系列规则](section-routing.md)确定主题、来源、文章形式与系列关系；技术内容读取[技术写作规范](technical-writing.md)。命中 Agent 文章或具体系列时，再读取根 `AGENTS.md` 指向的专项规则。

完成条件：已明确读者、前置知识、文章要解决的问题、可交付结果及本次修改范围。

### 2. 资料研究与论证设计

执行 `research-explainer`。读已有正文、源材料和与论点相关的实现，将关键主张对应到具体来源与条件；需要外部事实时核对一手资料，涉及版本或当前行为时重新验证。用案例、方案差异和会改变判断的条件组织论证。

完成条件：关键事实和比较有对应依据；拟题有足够材料支撑；假设、作者判断与来源结论能够区分。资料不足时缩小结论或说明具体缺口。

### 3. 起草或改写正文

执行项目 `humanizer` 的完整流程，包括其必读参考与交付前检查。按上一步的论证起草，用具体主体、动作和例子解释机制，首次出现的陌生术语给出必要解释。保留代码、引用及结论中的条件和限制。

完成条件：正文回答开头的问题，段落推进论证；已按易读性规则检查主要机制，补足漏讲的前提、指代和例子；每处新增事实有依据，润色没有强化结论或丢失原意。

### 4. 按需制作配图

结构、调用、状态或方案差异适合用图解释时，执行项目 `diagram-design`，先按其要求解析项目样式配置，再完成自身的生成与检查步骤。图片与文章资源同目录，技术主张仍使用前面已核对的来源。

完成条件：图中名称、边界与正文一致；图注或 alt 说明读者应观察什么；输出与引用经过检查。没有新增或修改配图时跳过本步。

### 5. 验证并交付

对照来源检查全文，核对 front matter、内部链接和资源；按任务范围运行代码与站点检查。发布任务按 [Hugo 发布规范](../hugo-publishing.md)执行；只修改内部规划或规则时检查引用与差异，记录适用检查的实际结果。

在已有内部规划、工作记录或交付说明中简要记录：执行的 skill 与范围、实际验证命令和结果，以及未完成项。执行记录保存在内部材料中，公开正文只保留读者需要的来源与复现信息。

完成条件：所选任务分支的必需步骤均有结果；正文任务的交付前理解检查已有记录，并区分自查与真实读者反馈；未运行的验证、未读的正文和缺失的依赖明确标注，交付状态与实际工作一致。
