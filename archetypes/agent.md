> 1. `title`：写清楚这篇文章真正要讨论的问题
> 2. `description`：一句话概括文章的核心内容与价值
> 3. `summary`：用于列表页展示，尽量简洁明确
> 4. `difficulty`：建议使用 `beginner`、`intermediate`、`advanced`
> 5. `article_type`：建议使用 `concept`、`tutorial`、`practice`、`review`、`eval`

## 这篇文章要解决什么问题

> 先用 2~4 句话说明：
>
> - 这篇文章讨论的核心问题是什么
> - 为什么这个问题重要
> - 这篇文章适合什么读者

## 先给结论

把最核心的观点先写出来，避免读者必须读完整篇文章才能知道你的判断。

可以考虑回答：

- 最推荐的方案是什么
- 不推荐的方案是什么
- 这个问题最容易被误解的点是什么

## 背景与动机

说明这个问题是怎么出现的。

可以从下面几个角度写：

- 你在实际做 Agent 项目时遇到了什么问题
- 为什么传统 workflow 或单轮对话不够
- 为什么这个问题在 Agent 场景下会被放大

## 核心概念或系统结构

如果这篇文章涉及概念分析，建议先定义概念；如果涉及工程实践，建议先给结构图或模块划分。

可以包含：

- 系统中有哪些核心组件
- 每个组件分别负责什么
- 它们之间如何协作

## 方案设计

这里写你真正推荐的方案。

建议按下面的顺序展开：

1. 目标是什么
2. 约束条件是什么
3. 方案核心思路是什么
4. 为什么这么设计
5. 有哪些替代方案

## 关键实现

如果文章偏工程，可以放关键代码、伪代码或流程拆解。

### 示例代码 / 伪代码

```python
# 用伪代码或最小示例解释关键逻辑

def run_agent(task: str):
    plan = create_plan(task)
    result = execute_tools(plan)
    return result
```

如果这篇文章不是代码实现类，也可以改成：

- 时序流程
- 状态变化过程
- 调用链拆解

## 常见问题与失败点

这一部分很重要，建议至少写 2~3 个真实问题。

例如：

- 工具太多导致选择不稳定
- 记忆加了很多，但效果没有明显提升
- 规划很复杂，但实际收益有限
- 模型看起来会做，但执行经常中断

## 如何评估效果

不要只写“感觉更聪明了”，尽量写清楚如何判断方案是否有效。

可以从这些角度出发：

- 成功率是否提高
- 平均执行步数是否下降
- 成本是否可接受
- 延迟是否可接受
- 是否更容易调试和复现

## 适用场景与边界

明确这套方案适合什么情况，不适合什么情况。

建议说明：

- 什么场景下值得使用
- 什么场景下用简单 workflow 就够了
- 什么时候不应该引入额外复杂度

## 总结

最后用 3~5 条要点回收全篇内容。

例如：

1. 这个问题的本质是什么
2. 推荐方案的核心优势是什么
3. 最大的代价或限制是什么
4. 下一步可以继续优化什么
